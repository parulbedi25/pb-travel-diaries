# PB Travel Diaries

A React/Vite travel site ("PB from PB — India, Unfiltered") with cinematic films,
road-tested routes and honest guides — plus a dashboard that edits the live site.

**Stack:** React 19 · Vite 7 · TypeScript · Tailwind CSS 4 · Express 5 ·
MariaDB. The site is served by its own Node process, so hosting needs Node and a
database.

Vite is a **build tool only**: it compiles the React/TypeScript source into
`dist/`. The deployed app is plain Node.js serving that folder, the API and the
media — no Vite, React or TypeScript on the server. `npm run package` produces
exactly that runtime-only folder.

- **[RUNNING.md](RUNNING.md)** — step-by-step: development on your computer,
  production locally, packaging an upload, and production on a server.
- **[DEPLOYMENT.md](DEPLOYMENT.md)** — hosting requirements, databases,
  backups, HTTPS, updates, process-manager examples.
- **[NAMECHEAP.md](NAMECHEAP.md)** — the same, written for Namecheap shared
  hosting: cPanel → Setup Node.js App, database names, upload, HTTPS, fixes.

## Where things live

| What | Where | Backed up? |
| --- | --- | --- |
| Site content, accounts, sessions, access history, media index | MariaDB | every day, into `backup/` |
| Uploaded photos and documents | `media/` | every day, into `backup/` |
| Installer answers (database password, site title) | `data/install.json` | re-created by a restore |
| Daily zips (database + media + code) | `backup/` | **copy them somewhere else too** |
| Assets that ship with the code | `public/` | in git |
| Built site | `dist/` | regenerated by `npm run build` |

Nothing that matters is kept in the browser. The old localStorage site is
imported once from **Settings → Bring this browser's site into the database**.
The single exception is a disposable cache of a third-party road route in the
live tracker, which holds no content, accounts or history.

## Requirements

- **Node.js 20.19+ or 22.12+** — Vite 7 dropped Node 18.
- **MariaDB 10.3+ or MySQL 5.7+** — locally, or from your hosting panel.
  The app creates the tables; you only create an empty database and a user.

## First run: the setup screen

Start the server and open the site. If there is no database configured yet, the
app shows a two-step setup screen instead of the journal:

1. **Website title + MariaDB details.** It tests the connection, creates the
   database (when the user is allowed to) and every table, then saves the
   answers to `data/install.json` (`0600`).
2. **The super-admin account.** One time only. It becomes the owner and is the
   only account the installer creates.

The same screen has a **Restore a backup** tab: upload one of the zips from the
old server's `backup/` folder and the database, its accounts and the media come
back — with the database name, user and password editable before anything is
written. See [Backups and restoring](#backups-and-restoring).

You never import `schema.sql`. If you prefer command-line configuration, put the
`DB_*` values in `.env` and run `npm run db:init`; the setup screen then skips
the database step.

Once a database has been configured the setup endpoints lock, so a visitor
cannot repoint the site at another database. Complete setup immediately after
deploying.

## Local development

The full walkthrough, including the server, is in **[RUNNING.md](RUNNING.md)**.

```bash
npm ci
cp .env.example .env      # optional — or use the setup screen
npm run dev               # API on :4000 + Vite on :5173, one terminal
```

Open `http://localhost:5173/`. Vite proxies `/api` and `/media` to the API, so
the browser sees one origin, exactly like the deployed app. The setup screen
opens by itself while the site has no database and no owner (`/#/setup` works
too). The dashboard is at `/#/admin`, the public account page at `/#/members`.

`npm run dev` starts both halves and stops both with Ctrl+C. If the API is
already running (for example from `npm run dev:api`), it reuses it instead of
failing on the port.

No database to hand? `DB_DRIVER=memory npm run dev` runs against an in-memory
store so the UI can be worked on. It forgets everything on restart and skips the
setup screen.

### See it exactly as it will be deployed

```bash
npm run prod              # build dist/, then serve it on :4000
```

That is the same Node server the host runs: no Vite, no separate API. Open
`http://localhost:4000/`.

### Build the folder you upload

```bash
npm run package           # dist/ + release/pb-travel-diaries/
```

`release/pb-travel-diaries/` contains only what runs — `server/`, `dist/`,
`public/`, the package files and the three guides. Copy it to the server and
run `npm ci --omit=dev` there; no build tools are installed or needed. See
[RUNNING.md §2.4](RUNNING.md#24-make-the-folder-you-upload-npm-run-package).

| Command | What it does |
| --- | --- |
| `npm run dev` | API + Vite together, hot reload, `/api` and `/media` proxied |
| `npm run dev:web` | Vite only (when the API is started another way) |
| `npm run dev:api` | The API only, restarting on server file changes |
| `npm run server` | Serve the existing `dist/` (no rebuild) |
| `npm run build` | Production build into `dist/` |
| `npm run prod` | Build, then serve exactly as hosting does (production mode) |
| `npm run package` | Build, then write the runtime-only upload folder (`release/`) |
| `npm start` | Serve the existing build in production mode |
| `npm run db:init` | Apply the schema using `.env` (optional; the installer does this) |
| `npm run schema:sql` | Regenerate `server/schema.sql` from `server/db/schema.js` |
| `npm run test:server` | API + installer tests (in-memory database, real HTTP) |
| `npm run preview` | Vite's static preview of `dist/` on :4173 (no API; use `npm run prod` to test the real thing) |

Vite and React are **build tools only**. At runtime the site is one Node
process (`server/index.js`) serving `dist/`, the API and `/media`; the host never
needs to run Vite. The six runtime packages are `express`, `mysql2`, `bcryptjs`,
`dotenv`, `multer` and `cookie-parser`.

## Environment variables

The setup screen is the normal route; `.env` is for CLI users and hosting panels.
Full list in `.env.example`, host values in [DEPLOYMENT.md](DEPLOYMENT.md).

| Variable | Purpose |
| --- | --- |
| `DB_HOST` `DB_PORT` `DB_USER` `DB_PASSWORD` `DB_NAME` | MariaDB connection (wins over `data/install.json`) |
| `DB_SOCKET` | Alternative to host/port on shared hosting |
| `DB_DRIVER` | `mysql` (default). `memory` only for local work and tests |
| `INSTALL_FILE` | Where the installer saves its answers. Default `data/install.json` |
| `MEDIA_DIR` | Where uploads are written. Default `./media` |
| `DIST_DIR` | Where the built site is. Default `./dist` |
| `SESSION_DAYS` | How long a sign-in lasts |
| `COOKIE_SECURE` | `auto` marks the cookie Secure over HTTPS |
| `TRUST_PROXY` | Keep `true` behind Passenger/nginx |
| `BCRYPT_ROUNDS` | Password hashing cost (10 on shared hosting) |
| `MAX_UPLOAD_MB` | Upload ceiling |
| `BACKUP_ENABLED` `BACKUP_HOUR` `BACKUP_KEEP` `BACKUP_DIR` | The daily backup: on/off, hour, how many zips, where |
| `BACKUP_INCLUDE_APP` | Put the application's files in the zip too (default on) |
| `MAX_RESTORE_MB` | Largest backup the restore screen accepts |
| `ALLOW_SITE_RESTORE` | `1` allows a restore over an installation that already has a database |
| `ALLOW_PUBLIC_SIGNUP` | Fallback only: the dashboard's **Allow public sign-up** setting wins once installed |

The browser-side build also reads `VITE_LIVE_FEED_URL` (optional) for the live
tracker feed. `VITE_*` values are inlined **at build time** and are public —
never put a secret in one.

## Data model

Eight tables — seven of data plus the migration ledger — defined in
`server/db/schema.js` and generated into `server/schema.sql`:

| Table | Holds |
| --- | --- |
| `site_content` | the published site (one JSON row) |
| `revisions` | the last 15 published snapshots, for rollback |
| `users` | accounts, bcrypt password hashes, roles (`owner`, `admin`, `reader`) |
| `sessions` | server-side sessions (SHA-256 of the cookie token only) |
| `auth_events` | sign-up / sign-in / sign-out / failed attempt history with IP |
| `media` | index over the files in `media/` |
| `settings` | site title, public sign-up switch, theme, schema version |
| `schema_migrations` | which migrations this database has run (see below) |

**Changing the schema later.** New columns, tables and data changes are entries
in `server/db/migrations.js`, applied by the next boot or `npm run db:migrate`;
`schema_migrations` makes sure each one runs exactly once. A brand-new install
replays the same list, so old and new databases end up identical. Full
instructions in [DEPLOYMENT.md §9](DEPLOYMENT.md#9-changing-the-database-later).

**Blanked sections repair themselves.** The published JSON stores only what a
section needs; anything it leaves out falls back to the content built into the
app. A slot that is present but *empty* is different — it wins, and the section
shows nothing. If a saved site ever comes back with My Picks, the live
tracker's stops, a section's copy or its photos empty, the app fills those slots
from the built-in content once, marks it with `restore-default-data-v1` in the
content's migration list, and leaves later edits alone. Dates, schedules and
uploaded files are never filled in.

**`locked` is never stored.** It is a note the server adds to one response for
one visitor, and it is removed again on the way in — from a published snapshot
and from any response to a signed-in user. A members-only section still closes
for a visitor who is not signed in; a section that is not members-only can
never show the members-only card.

Passwords are never stored or logged in clear; the browser holds only an
httpOnly session cookie it cannot read.

## Accounts and the members area

- The **owner** is created by the setup screen and can never be deleted.
- **Admins** edit and publish. Add them in **Settings → Accounts**.
- **Readers** sign up at `/#/members` (when public sign-up is on) or are added by
  an owner/admin. They can sign in and read the members-only sections; every
  write and every account-management call returns 403 for them.
- **Members-only sections:** each section in the dashboard has a **Public /
  Members** switch. Visitors get a locked card with the section's name; signed-in
  accounts get the real content. The server removes the data from the anonymous
  response, so it is not merely hidden with CSS.
- **Disabling an account** (**Settings → Accounts → Disable**, or
  `UPDATE users SET disabled = 1` in the database) signs it out everywhere and
  closes the members-only sections to it. Signing in says the account is
  disabled — but only after the password is right, so the form still cannot be
  used to discover which accounts exist. Everything public stays readable
  without signing in.
- Every sign-up, sign-in, sign-out, failed attempt, password change and account
  creation is recorded in `auth_events` and shown in **Settings → Access history**.

## Admin (PB Control)

The dashboard is at `#/admin` (aliases: `#/pb-control`, `#/login`).

- **Saving** writes the whole site to `site_content` and a snapshot to
  `revisions`, in one transaction. If the write fails, the live view rolls back
  and the draft is kept, so nothing is lost.
- Signing in lasts `SESSION_DAYS`; changing a password signs out every other
  browser. Signing out deletes the server session.
- **Settings → Site & sign-up** sets the browser-tab title and whether strangers
  may create read-only accounts.
- Scheduled maintenance still evaluates on each visit; the state is persisted by
  the next save.
- **Backups** tab: the daily schedule, the archives on disk, **Back up now** and
  a download link for each one.

## Backups and restoring

Once a day the server writes one zip into `backup/` at the root of the
installation and keeps the newest ten. Each zip holds the whole database as a
standalone `pb-restore.json` importer (accounts, password hashes, content,
revisions, media index, every setting), the uploaded `media/`, and the
application's own files.

To put one back: deploy the code on the new server **without** `data/`, open the
site, choose **Restore a backup** on the setup screen, upload the zip, correct
the database name/user/password if this server differs, and press restore.
Every account, image and setting comes back — you sign in with the password you
already had.

Details, the schedule variables and the by-hand alternative are in
[DEPLOYMENT.md §8](DEPLOYMENT.md#8-backups).

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| The setup screen appears although `.env` is filled in | The app cannot see those variables — set them in the hosting panel or fix `.env`, then restart. |
| “The database is not answering” | The saved credentials stopped working, or MariaDB is down. Fix them in your hosting panel; for `data/install.json`, edit or remove it and reload. |
| `/api/health` says `"database":"memory"` | `DB_DRIVER=memory` is set; production must be `mysql`. |
| Site shows built-in content | Nothing published yet — sign in and press Save Changes. |
| Saves say “Sign in to continue” | The session cookie is not surviving: check `TRUST_PROXY=true` and HTTPS. |
| White page, console 404s | `dist/` is stale or missing — run `npm run build` and restart the server. |
| Built-in images 404 | Run `npm run build` (they are copied from `public/`); uploads live in `media/`. |
| Uploads fail | Check `MEDIA_DIR` exists and is writable. |
| Live tracker never updates | `VITE_LIVE_FEED_URL` was added after the last build — `VITE_*` is inlined at build time. |
| `npm ci` fails on Node 18 | Vite 7 needs 20.19+ or 22.12+. |
